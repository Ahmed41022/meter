# Architecture

How Meter is built, and why each decision is the way it is. Most of what
follows exists to avoid a specific way of getting the numbers wrong — the
failure is named alongside the choice that prevents it.

For what the app *does*, see [FEATURES.md](FEATURES.md).

---

## Why it's built this way

Most of the design here exists to avoid a specific way of getting the numbers wrong.

**Elapsed time is derived, never accumulated.** The obvious implementation is `setInterval(() => seconds++, 1000)`. It's also wrong: browsers throttle background tabs to roughly one tick per minute, and a sleeping machine stops ticking entirely. Since you're working while the tab is backgrounded, that's every session. A session instead stores `startedAt` as an epoch integer and computes `now - startedAt` on read. The interval exists only to trigger a re-render — kill it and the stored data is still exact.

**Money is derived from time, and summed as integers.** Earnings are `elapsedMs / 3600000 * rate`, computed fresh, rounded once to minor units at the boundary. Nothing accumulates a running float, and no total is ever cached — deleting a session would immediately make a cached total lie.

**Rates are snapshotted onto sessions, and a task can override them.** `project.currentRate` is the default for the *next* session; `session.rate` is what that session recorded. Changing your project rate reaches back only as far as you say: *from now on* it moves the sessions of tasks still open and leaves work already handed in, and work filed under no task, on the rate they recorded; *past included* it moves every session on the project except under a task with a rate of its own. Either way it is an edit to `session.rate`, stamped and synced like any other, and the second can be undone in one step. But that snapshot is a *projection* of what you'll be paid, and the real figure is often settled later — at submission, or when the client says so. So a task can carry a rate, and every session filed under it is valued at that rate instead.

The split that makes this safe: **hours are a measurement, rate is a parameter.** `segments` record what you actually worked and stay immutable. The task rate lives on the task, never overwriting `session.rate`, so the original snapshot survives as an audit trail and clearing the override restores it.

**A time limit is a line across a task's hours, not a stored deduction.** Where a platform pays a task's time in full only up to a limit, the time over it pays a share of the rate. Which time is over is derived on read: the task's billed segments are laid end to end in the order they started, and the moment their total reaches the limit is the line. `pricer` in `domain/terms.js` hands back the `rateOf` every money figure already took, with `rateOf.limit(session)` saying where that session's task crossed; `sessionCents` splits a session's time in a window at that moment, so a day's figure carries only its own share of each side. Every money figure goes through it — no screen multiplies a rate by a duration itself — so none can disagree about what a sitting came to. The limit lives on the project as a history, `taskLimits`, so a change can be made from now on: a task handed in is held to the entry in force at its hand-in, a task still open to the latest.

**A session is a list of segments, not a start/end pair.** Pause and resume append a new `{startedAt, endedAt}` interval, so the gap between them is never billed. Modelling this up front avoids migrating every record later.

**Time is an argument, never ambient.** No function in `src/domain` calls `Date.now()`. The caller passes `now`. That single constraint is what makes the entire rules layer testable without mocking a clock.

**Crash recovery bills the last heartbeat.** A running session writes a `lastTick` every 60 seconds. If the app reopens and finds a session that claims to be running but stopped checking in, it offers to close it at the last heartbeat rather than silently billing the eleven hours you were asleep.

**Idle time shares the state machine but never the total.** Time at the desk that wasn't worked is a session with `kind: 'idle'` — same segments, same pause/resume, same crash recovery. What keeps it out of your earnings is the accessor shape: `sessionsFor()` returns billed sessions only, and idle time has to be asked for by name. A caller that forgets about kind under-reports idle time, which is harmless, rather than inflating income, which is not. Starting either timer stops the other one, on any project, because one person can't bill two things at once.

**Tasks are records, not strings on a session.** A free-text label splits on a typo — "1234" and "1234 " become two rows with the earnings divided between them, silently. So a task is a record on the project and a session holds its id, matched trimmed and case-insensitively. Starting the meter asks which task first, as an explicit existing-or-new choice, because that is the moment a duplicate would be created.

**A finished session can be corrected, and the original is kept.** Immutability was there to stop records drifting by accident. But a session you forgot to stop is already wrong, and a wrong figure you can't fix is worse than one you can. What deserves protecting isn't that the number never moves — it's that you can always see what the meter actually recorded. So a correction writes the new window into `segments` and stashes the as-recorded ones under `original`, which only the *first* correction fills: edit twice and `original` still holds the measurement, not your previous guess. Reverting restores it exactly.

Corrections preserve pause structure rather than collapsing a session into one start→end block. Collapsing a session with a four-hour break would silently bill the break — so the editor previews the resulting duration, which is rarely just end minus start.

**Re-filing is separate from correcting.** `taskId` is a label on the record rather than part of it, so moving a session between tasks changes which bucket the same hours report under. That needs no `original` and leaves segments, rate, kind and closedAt untouched — there are tests asserting exactly that.

**Deleting a task unfiles its sessions rather than orphaning them.** The hours stay recorded and reappear under "No task", and the delete is undoable.

**Money in two currencies is never added without a rate.** This is the app's central invariant, and it has four parts. Stored money is never converted or rewritten: every amount stays in the currency it was earned in, and a conversion is a display figure worked out fresh from the stored ones. A converted figure is always marked (`≈`) and carries the rate date, so an estimate cannot pass for a record. Nothing that writes to the ledger reads a converted figure: answering a payment stores the row's own currency and cents, whatever is on screen. And with live rates off, the default, the app behaves exactly as it did without them and never touches the network.

**Rates are public data, so they are a per-device cache, not ledger.** `fx/rates.js` fetches one file of units-per-USD from two hosts (the CDN first, then the Pages mirror) with `cache: "no-cache"`, because the CDN tells browsers to keep it for a week, and a timeout that does not depend on the fetch honouring its signal. The last good copy lives under `meter:rates` in `storage/settings.js`, beside the theme, and is not synced; it is stale when from an earlier day, 12 hours old or more, or stamped in the future. `useRates` loads it and checks again about every 6 hours, and does nothing at all (no read, no fetch, no timer) while `fxOn` is false. The choices that follow the owner are synced preferences, one record each: `fxOn` (default off), `displayCurrency` (a code or `earned`, default USD) and `favourites` (a non-empty list of unique codes, default USD); `setPref` compares arrays item by item so an unchanged list is not stamped as an edit.

**Conversion is arithmetic in `domain/fx.js`, and the decision about what to print is in `domain/fxDisplay.js`.** `normaliseRates` accepts only a feed with a real date and a `usd` table, skipping keys that are not three-letter codes and entries that are not positive finite numbers, and pins USD at 1. `convertCents` goes through USD and rounds once, to the nearest cent with halves away from zero, so a refund converts to exactly the negative of the same payment; the same currency is returned untouched. `convertFigures` converts and rounds each currency separately and adds, flags `converted` when any non-zero figure changed currency, and returns `null` cents with the missing codes rather than a total that quietly leaves a currency out. `displayMoney` converts only when the choice is a currency, rates are on and present, and every currency in the figures has a rate; otherwise it returns each currency as earned, in the order the caller already used, and says why (off, none, missing). The UI reads it through `CurrencyContext` and `useMoney`; individual records never go through them.

**Money is ranked inside one currency, or in the display currency.** `domain/order.js` is the one place lists are ordered by money, and it keeps the invariant above. Rows are grouped by currency; the groups are laid out most hours worked in that currency first (ties and lists with no hours by code), and inside a group the biggest comes first. A row with money in several currencies is placed by its biggest single-currency figure, in that figure's currency, never by a sum. Rows with no money sink to the bottom whichever way the sort points, and ties keep the order the rows came in. Turning a sort round flips it inside each group and leaves the groups where they are. `orderByMoney` takes the group order as an argument, which is the seam for the converted ranking: `orderByMoneyIn` asks `convertedFigures` for every row's money as one figure in the display currency, and those figures, all in one currency, go through the same function as one group. It is all or nothing: if rates are off, the choice is `earned`, or any row holds a currency without a rate, the list keeps its grouping, so converted and unconverted rows are never ranked against each other. Ranking by an hour is the same rule over rates, so it too stays within one currency.

**Merging is generic, and a tie has one answer.** `mergeState` merges every top-level list of records (arrays of objects with ids), found by shape from the keys of both sides, not only the `COLLECTIONS` this build knows. A filter by name made an older device drop, on its next sync, any list a newer build had added; now such a list survives and round-trips. `stampChanges` iterates the same keys, so an edit to a list this build does not know is stamped and sent. A top-level value that is not a list has no stamp to arbitrate, so it keeps mine and takes theirs only where mine has nothing, apart from `lastBackupAt`, which takes the later. Where two copies of a record carry the same `updatedAt`, the one whose JSON is greater wins. "Mine wins" cannot converge, because each device keeps its own copy and they disagree for ever; this is arbitrary but identical on every device, and identical copies, the usual tie, are left as they are. Theirs is indexed in a `Map` once, where scanning it for every record made a ledger of a few thousand sessions slow. Nested arrays inside a record (a project's tasks, a session's segments) still merge with the record, whole: two devices editing different tasks of one project in the same window lose one edit.

**Deletes are soft.** Sessions get a `deletedAt` and drop out of totals, with an undo. Hard-deleting financial records with no undo is a decision you regret exactly once.

**Timestamps are UTC epoch integers; only display is localised.** Goal periods bucket in local time, because "this week" means the user's week — but the boundary is derived from a `Date` rather than wall-clock strings, so it stays correct across a DST transition.

## Data

Everything lives in browser storage under `meter:v1`. A stored value that cannot be read is copied to `meter:v1:unreadable:<ISO time>` before anything is written over it, and nothing is saved at all where no copy could be made. The ledger is:

```js
Project    { id, name, currentRate, currency, createdAt, sessionGoal, overallGoal,
             offClock?, company?, status?, statusAt?, paysOnAcceptance?,
             perTask?, bonusPerHour? }
Earning    { id, projectId, taskIds?, kind, cents, currency, at, note, units?, sessionId?, status?, payday?, received?, receivedOn?, createdAt, deletedAt }
Payout     { id, client, currency, scheduled, outcome, movedTo?, expectedCents?, receivedCents?, adjustmentId?, answeredAt, createdAt, deletedAt }
Objective  { id, projectId, text, done, doneAt, createdAt, focusedOn, estimateMs, taskId, deletedAt }
TaskLimit  { from, ms, factor }   // project.taskLimits?: TaskLimit[]
Todo       { id, text, projectId, done, doneAt, createdAt, deletedAt }
Company    { id, name, payPeriod, history?, createdAt, deletedAt }   // history: [{ rule, until }]
Pref       { id, value, createdAt, deletedAt }   // id is the key, e.g. "overviewPeriod"
Project  { ..., taskLimits?, tasks: [{ id, label, createdAt, rate, price?, note?, state?, stateAt?, submittedAt?, limitMs?, hoursReceived?, hoursPayday?, hoursReceivedOn? }] }
Session    { id, projectId, kind, taskId, rate, currency, createdAt, segments[], closedAt, deletedAt, original?, manual?, device? }
Segment  { startedAt, endedAt, lastTick }
```

An `Earning` is money with no duration anywhere on it — no segments, no rate — because it was never paid by the hour. `kind` is `'piece'`, `'bonus'` or `'adjust'`, and `units` records how many accepted items an amount covers. `taskIds` is a LIST, because one payment can cover many tasks: a platform that pays a reward for finishing fifty writes one line, and those fifty still need to know they were paid for. Absent means money no single task can be pointed at. A build before this wrote a singular `taskId`; that is still read and never written again, so no record holds two answers to one question, and money from a shared line is never divided between the tasks it names — a fiftieth of a milestone is a price nobody quoted. `sessionId` points from the money back to the stretch of tracked time that produced it, from the many to the one, so one sitting can yield an accepted task and an accepted changelist at two different prices without any list being kept in step. On both sessions and earnings a `status` of `'pending'` or `'cancelled'` says the money has not landed or never will; **absent means settled**, so nothing written before pay states existed changed meaning. `paysOnAcceptance` is absent on ordinary work and `true` where a session should start out pending. What acceptance is WORTH is a separate question with two possible answers, and a project holds exactly one of them: `perTask` is a flat amount per accepted item, and `bonusPerHour` is an extra hourly rate paid for every hour worked on the task once it lands — a project at 80 with a bonus of 10 pays 90 an hour for work that is accepted and 80 for work that is not. The two are alternatives because a project holding both would have two answers to one question; the settings form always writes the other null, and `rewardModel` prefers the hourly one if a merge ever produces both. The distinction is not cosmetic: a flat amount credits the same for a task that took twenty minutes and one that took six hours, which is wrong in both directions at once. Both are absent on a project that pays nothing extra on acceptance. A task's `state` is `'submitted'`, `'accepted'` or `'cancelled'`, and **absent means open** — still being worked, which is what every task written before this existed says. All three named states are terminal FOR TIME: `startSession` and `addManualSession` both refuse a task that has one, because the platform priced what it received and minutes added afterwards are minutes nobody is paying for. Submitting stops any meter still running on the task, counts its hours as earned where the project pays as worked or leaves them pending where it pays once accepted, and files the acceptance reward pending — one per task, re-priced rather than written again if the task comes back. Accepting pays the hours and the reward; rejecting cancels the money of both and leaves the hours on the record, in every time figure. Reopening an answered task puts its money back to pending until it is accepted again; `settle.js` owns all of this, and `taskState.js` only records where a task is. `stateAt` stamps when the CURRENT state was set and `submittedAt` when the work first went in; both are cleared on the way back to open. Both are the moment the work ACTUALLY went in and came back, to the minute, chosen in the settle bar and correctable on the task afterwards — not the moment the button was pressed, which used to push work handed in on a Saturday and ticked off on a Monday a whole pay period late. Which of the two decides the pay run a task's money is in, hours and reward together, depends on how the project pays: the ANSWER where it pays once accepted, because a run covers the tasks accepted during a period; the HAND-IN where it pays as worked, because there is no answer to wait for. Either decides that and nothing else, so it never reaches an amount. The hand-in is also the record of delivery — what a bonus window or a query about a slow review turns on. Two fields rather than one because the answer would overwrite the hand-in and lose the day the work went in. An earning's `payday` is a date, "2026-11-25", on the client's clock, chosen by hand; absent means the schedule dates it from `at`, so the default follows the schedule when it changes. `received` is `true` on money that has already been paid out and is never forecast; absent means not yet. Money naming no task, or a task's own money with a `payday`, is a line of its own in Upcoming payments, and a shared reward honours both fields too. `currency` is the earning's own and is not always its project's: a EUR bonus on a USD task is a EUR line, and an adjustment to a payment is in the payment's currency. A `Pref` is one preference that follows the ledger between devices: one record per key rather than one record holding them all, so a change to one on the phone and another on the desktop both survive the last-writer-wins merge. `domain/prefs.js` holds the registry of known keys, each with a default and a validator, and an unknown key or a value this build does not understand reads as the default; `prefs` is absent on a store written before it and reads as every default. Preferences are settings, not work, so they are left out of the counts of unsaved records and of what a restore replaces; a backup and a restore carry them like any other list. Six keys name the order a list opens in (`cardsSort`, `lifeSort`, `byProjectSort`, `byCompanySort`, `earningsSort`, `sessionsSort`). The value is the order's key and not its direction, so it stays a plain string that merges and validates simply: each order opens the way it is first read (names A to Z, everything else biggest or latest first), and turning it round is a question for the moment. Life has its own key because Earned is valid for Work and not for Life. Per-device choices (the theme, the period last looked at) stay in `storage/settings.js` and never sync. A `Company` is the first thing here to need a record of its own, and its id is the folded name, so two devices that both write "Outlier" converge on one row rather than merging into two schedules that disagree. `payPeriod` is `{ kind, cutoff, payday, after, closesAt?, zone? }` — weekly with ISO weekdays (Monday 1), or monthly with day-of-month numbers clamped to the length of the month, so the 31st is the 28th in February rather than the 3rd of March — or null for a client with no stated payday. Absent means no schedule and nothing forecast, which is what every store written before this existed says. `closesAt` is the minute of the cutoff day the period shuts at and `zone` the IANA name of the clock it is read on, because the platforms state a cutoff as an instant on theirs — “Sunday 7pm Eastern” is two in the morning in Cairo; both absent mean midnight on this device, which is what every rule meant before either existed. The zone's offset is read through `Intl` at each instant and never remembered, and a zone this browser does not know is kept as written rather than dropped, since another device may know it. `history` is absent on a schedule that never changed; replacing one appends the old rule with `until`, the moment it was replaced, and saving the same rule again appends nothing. A payday that had already passed under an old rule when it was replaced keeps its date, and one still to come follows the next rule, so answers filed under past dates stay attached to them; work dated after every change, and any floor dated from now, follows the current rule alone. A payday is a calendar DATE on that clock, carried as one all the way to the screen: an instant read back on another clock lands on the day before for any client east of the reader. The forecast itself is never stored: a written-down payday would be wrong the moment a schedule changed, and wrong silently. What the owner says about a forecast payment is, in `payouts`, because it is not derivable. A payment is a row of the forecast, one client (its folded name), currency and SCHEDULED date, which is the date the forecast gave before any answer, so moving a payment does not change which payment an answer belongs to; there is at most one live answer per payment, and answering again replaces it in place. `outcome` is `paid` (closed; without `receivedCents` it came exactly as forecast, which is what an answer written before amounts existed says), `cancelled` (closed, and `receivedCents` is what came regardless), `moved` (on `movedTo`, nothing yet) or `partial` (`receivedCents` so far, the rest on `movedTo`, and receiving more adds to it). `expectedCents` is the forecast at the FIRST answer and later answers keep it, so a change to the tasks does not rewrite what a difference was a difference to. Money is touched only when a payment closes: what came less what was expected is written as an `adjust` earning in the payment's currency, on the project most of the row came from, with `received: true`, and `adjustmentId` links to it. Answering again or taking an answer back replaces or restores both together. Taking one back is a stamped edit, a record rebuilt or tombstoned and never removed, because a record that merely vanished would be brought back by the next sync. A dated row whose day has passed is listed as overdue rather than dropped. Some LINES of a payment can be marked without answering the payment, and that word is kept on the lines' own records rather than in `payouts`: an earning's `received` or `payday`, and for a task's hours, which have no record of their own, the task's `hoursReceived` (`true`, never forecast; absent means not yet) and `hoursPayday` (a date of their own; absent means the task's payday). Hours moved that way leave the task's other money where it was. A line marked paid came as listed, so no money is written; a line moved onto a day this client's payment was already answered for is refused, since it would vanish with that answer. `payouts` is absent on a store written before them and reads as none. `status` is absent on a running project and `'paused'` or `'done'` otherwise — absent reads as running, and one field rather than two flags because a project cannot be both. `statusAt` stamps when it stopped and is cleared on the way back, so a project running again never reports a range that ended. `company` is absent or empty on work with no client named; it is the key every company figure is grouped by, so it can become a record of its own later without a migration. `manual` is absent on anything the meter recorded and `true` on a block entered by hand — absent reads as measured. `objectives` is absent on a store written before they existed and reads as none. `focusedOn` is a local `YYYY-MM-DD` and an objective is today's only while it matches today — so the pick expires on its own rather than needing to be cleared. `estimateMs` and `taskId` are both nullable: an objective with neither is a plain checklist item. `taskLimits` is absent on a project that has never had a time limit, and absent means none. An entry's `from` is when it came into force, null for always; `ms` is the limit, null for none from then on; `factor` is what an hour over it pays as a share of the rate, 0 for nothing. A task's `limitMs` replaces the project's limit and keeps its share, and is absent where the task follows the project. `todos` is absent on a store written before them and reads as none. A to-do is not an objective: it belongs to no project and measures nothing, so `projectId` is null unless one is named, and then only says which meter it can start; a to-do naming a removed project reads as unlinked rather than going with it. `offClock` is absent on a work project and `true` on one you track but don't work — absent reads as work, so nothing written before the setting existed changed meaning. `original` is present only on a corrected session and holds `{ segments, closedAt, correctedAt }` as the meter first recorded them. A task's `rate` is nullable — null means "value each session at the rate it recorded". A task's `note` is free text and absent when there is none; nothing groups, matches or reports on it, which is exactly why it can hold the ids and links a label cannot. A session's `device` names the copy of the app that opened it, absent on anything written before devices were told apart and read as "this one". It exists because a meter running on another machine and a meter that crashed are otherwise identical from here — both are a session whose heartbeat stopped arriving — and only the device that started it may write proof of life. The heartbeat is deliberately written WITHOUT an `updatedAt` stamp, so a machine ticking once a minute cannot out-date a stop made somewhere else; that is what lets a session be stopped from any device. `taskId` is nullable — sessions without one group under "No task". Projects saved before tasks existed have no `tasks` array and read as having none. `kind` is `'billed'` or `'idle'`. Sessions written before idle tracking existed have no `kind` at all, and that absence reads as billed — no migration needed, because nothing about the existing data changed meaning. The key is versioned so a real schema change can migrate rather than clobber.

**The payment history is the forecast's past, derived from the same rows.** `domain/payHistory.js` does not keep a list of what was paid. It asks `forecastRows` in `payout.js` for every payday, the same builder Upcoming payments uses, so a payment is on the same day in both and a schedule changed since leaves the past where it was (`paydayThrough`). What it adds is what you said: the answers in `payouts`, and the lines marked paid one at a time. A row is one client, day and currency and carries a status (`paid`, `partial`, `cancelled`, `unanswered`, `lines-paid`), `lines` (what the payment is made of) and `paidLines` (kept apart, so a row's expected and received are the payment's own and `paidLinesCents` sits on top). Totals are a map by currency and nothing is ever summed across one; a display-currency total is the UI's, never the model's or the CSV's.

**A paid line's date is recorded when it can be and inferred when it cannot.** Marking a line paid writes `receivedOn` (an earning) or `hoursReceivedOn` (a task) as the payday of the row it was on, a plain day on the client's calendar. A line marked before that existed, or money added as already paid, has none. A forecast drops a paid line, so without a day nothing would remember which payday it was part of; the history therefore dates it by the rules, from its hand-in, its acceptance or the day it was added, on the schedule as it stood then, and marks it `inferred: true`. The CSV turns that flag into its *Dated by* column (`recorded` or `schedule`), so a spreadsheet can tell a fact from a worked-out date. A client with no schedule has no payday to give, so its money has no place in the history. Moving a line, or taking its mark off, clears the day: a line that is not paid was paid on no day. Spans (`statementPeriod.js`) are inclusive pairs of days, never instants, and the chosen span is a per-device setting (`meter:statement-period`), unpacked forgivingly so a value from a future build opens on the default.

Browser storage evaporates — a cleared cache takes your ledger with it. **Export a backup** from Settings periodically; it writes plain JSON that Restore reads back.

## Sync

A device with no account keeps its ledger in the browser alone. Two ways to share it exist. **Google Drive** (`sync/drive.js`, `google.js`) reads the whole file, merges, and writes it back, with no compare-and-swap. It stays through a two-week grace period and is not used by a device that has a Meter Sync account. **Meter Sync** is described here: record-level, end-to-end encrypted, through a relay the owner runs. The principle is the one the rest of Meter follows: the merge is what makes it safe, and everything else is built so that a failure costs a retry and never a record.

### What goes over the wire

The relay keeps an **append-only log of encrypted change batches**, each given a `seq` by the relay, and one **latest snapshot**: the whole ledger as of some `seq`. A batch is `{ v, changes: [{ k, r }], meta: { lastBackupAt } }`, where each change is a **whole record** and not a field patch, so what happens on receipt is exactly the merge of `domain/merge.js`: the higher `updatedAt` wins, with the deterministic tie. That merge is commutative and idempotent, so the order of the log does not change the result and a replayed batch is harmless. This, not the compare-and-swap below, is what makes the design safe.

**What a device sends is worked out, not tracked.** `meter:sync:sent` maps `"collection/id"` to the `updatedAt` the relay acknowledged. A record is pending when it is newer than its entry or has none: one scan, with no dirty set written at every commit to desync on a crash. A map was chosen over a single watermark because a record received from a fast-clocked device would raise the watermark above local time and strand edits made earlier. Losing the map fails safe: everything is pending and one idempotent re-push follows. A received record that wins the merge is marked sent at its own stamp, which is what stops echoes; one whose local version won stays pending. The engine writes a pulled state with `write`, never `commit`, because it is news and not an edit: stamping it would re-date every record that just arrived and send them all straight back.

**Heartbeats and liveness never enter the ledger.** `lastTick` stays local and unstamped, so it creates nothing pending and never reaches the log. A started, stopped or resumed session is an ordinary stamped edit. That a meter is running somewhere is a **presence** message over the live connection, sent once a minute by the device holding it, encrypted like everything else, relayed and forgotten. It lives in a ref and is used only for "Running on <device>"; it is never merged and never saved.

**A round is pull, push, then now and then compact.** Pull first so everything unseen is merged before writing, which lets the overlap and two-meters warnings run before the write. Push is `POST /log { epoch, expect, bid, blob }`: the Durable Object runs one request at a time, so check-and-insert is atomic, and `expect` must be the current head. A mismatch returns `409` with the entries the device lacks, so the retry costs no extra read; three retries in one round, then it reports busy and waits. `bid`, a random 128-bit id chosen by the client, is unique, so a retry after a lost response returns the existing `seq`. A device too far behind gets `410` and fetches the snapshot, merges it, sets its cursor, and reads the tail; after any adoption of a snapshot (joining, a relay recreated) it **reconciles**, marking records no newer than the snapshot's as sent so a new phone does not re-send its whole ledger. After 200 batches a device that is caught up uploads a snapshot with a compare-and-swap on `expectUpto`, so two compacting at once cannot both win, and the log keeps a short tail so a device slightly behind skips the download. A snapshot is the ledger as JSON, gzipped (`CompressionStream`), then encrypted and cut into parts of at most 1 MB. Tombstones are never pruned, since a pruned one lets a stale device resurrect a record.

**The batch carries a version.** A build that meets a `v` newer than it understands applies nothing and reports `needs-update`; unknown collections are applied generically and unknown fields are kept, because whole records are replaced. This is why devices that sync should run the same version.

### Encryption

Everything is WebCrypto, with no dependency. The vault key `K` is 32 random bytes per epoch. `encKey` and a recovery authenticator are derived from it by HKDF-SHA256 with distinct `info` strings, so the same secret is never asked to do two jobs. Each message is AES-GCM-256 with a random 96-bit nonce, which at personal scale makes a collision negligible and needs no counter shared between devices. The **associated data** is `meter|v1|<epoch>|<kind>|<ctx>`, where kind is `log`, `snap`, `presence`, `name` or `keybox` and ctx is the batch id for a log entry, `upto|part|parts` for a snapshot part and the device id for a name or keybox. That stops the relay moving a ciphertext to another role, epoch or part, and makes truncating or swapping snapshot parts fail. It does not stop the relay dropping, delaying or reordering log entries or serving an old snapshot; the merge tolerates reorder and duplicates, and the rest is out of scope for a relay the owner runs, and the app says so. Plaintext is padded to the next power of two (256 bytes at least) so the relay sees a size bucket and not a length. Compressing before encrypting is acceptable because nobody but the owner supplies plaintext, so there is no oracle to learn from the length.

`K` is kept per device in `localStorage` (`meter:sync`, with `meter:sync:meta`, `meter:sync:sent` and the pairing and acknowledgement keys beside it), never in the ledger or the JSON export, with a test pinning that. It has to be extractable bytes to be shown again as a recovery code and wrapped for a new device, and the plaintext ledger already sits in the same storage, so protecting `K` from same-origin script would protect nothing extra: the threat model is the relay and the network. Anyone with the browser profile has both; device encryption is the answer to that. Each device also has an ECDH P-256 pair that exists only to hand `K` to a specific device.

### Pairing and authentication

A device authenticates every request with a **per-device bearer token**: 32 random bytes of which the relay stores only the SHA-256. A WebSocket cannot set headers, so the token travels as a subprotocol (`meter.v1`, token) and never in a URL or an access log.

Pairing is **approval pairing authenticated by a secret the relay never sees**. Six digits are about twenty bits, and a relay that sees both public keys could grind key pairs until the digits agree, so the digits are not what stops a malicious relay. The first device makes a 128-bit secret `S` and a join id and tells the relay only the join id and the hash of a join token derived from `S`; `S` travels in the QR or typed code alone. That code (relay host, vault id, join id, `S`, a checksum that covers the host) holds **no key**, expires in ten minutes, and lives only in a URL fragment: a code found in a query string is rejected, and the app removes it from the address once read. The joining device sends a request carrying a proof computed from `S`; the first device **verifies it before showing anything**, so a request from someone without `S` never reaches the screen. The six digits are a hash of both public keys **and `S`**, shown on both screens, and are the owner's check that this is the phone in their hand. On approval the first device sends `K` wrapped to the joiner's public key (ephemeral-static ECDH, HKDF with both public keys in `info`, AES-GCM) with an acknowledgement MAC over both keys and the epoch; the joiner **verifies it with `S`** before unwrapping, so the key is proven to come from the holder of `S`. Both devices save their keys and secret before sending anything, so a crash resumes with the same identity. Not covered, and said plainly: someone holding `S` can ask to join within ten minutes, and the owner's check of the digits and the device name is what stops them.

The recovery code is `K` itself as Crockford base32 with a checksum, eight groups of eight. A device holding it can prove possession to the relay (`POST /recover`, rate limited) and register as a new one; the relay endpoint and client call exist and are tested, and the screen to use them is not built yet. Removing a device is a **key rotation** (`POST /rotate`: a new epoch, a fresh snapshot, `K'` wrapped for every remaining device, the removed token deleted, the log emptied), which the relay implements and its tests cover; the client side and the Remove button are not built, and the button is shown off.

### The relay

`relay/` is deployed on its own and never bundled into the app. It is plain JS logic over an injected `sql`, clock and random source, hosted by thin classes, so the same code runs in a Durable Object, in a test over `node:sqlite` and under a frozen clock.

- **`worker.js`** is the Worker. It validates cheaply and forwards, and settles CORS, the method and path allowlist, the shape of the `Authorization` header, body size caps and the account id's check **before any Durable Object is touched**, because a Durable Object is created by merely naming it and every request to one is billed. Junk costs a Worker request and nothing durable. CORS is open (`*`): authentication is a bearer header with no cookies, so CORS would protect nothing and an allowlist would only force the Pages origin into the deployment.
- **An account id** is `<128 random bits as 32 hex>.<16 hex mac>`, the mac an HMAC of the random part under `ROUTE_KEY`, a Worker secret. Only an id this relay minted routes to an object. Changing `ROUTE_KEY` orphans every account.
- **`vault.js`** is one account, one SQLite-backed Durable Object: `meta` (epoch, head, snapshot position, recovery hash, counters), `devices` (token hash, public key, an encrypted name, added and last seen), the `log` (`AUTOINCREMENT`, so a pruned `seq` is never reused), `snapshot` parts, `keybox` and `pair`. It never reads a blob: log entries, snapshot parts, wrapped keys and names are stored and returned untouched. `head` lives in `meta` so it survives pruning the log to empty.
- **`registry.js`** is the one registry object: who may create an account and how many exist. Invites are stored as their SHA-256 (the code is shown once), with a label, an expiry and, once used, the account id. Consuming an invite, checking the cap, minting the id and recording the account are **one transaction**, so two people spending one invite cannot both win, which is why it is a Durable Object and not KV (eventually consistent, and a small write allowance). If the follow-up that initialises the account fails, the invite is already bound to that id, so the client retries with the same invite and gets the same account. In open mode creation needs no invite but is limited per address (three a day by default) and in all (50 a day); an address is kept only as a hash salted afresh each day, so counting leaves no log of addresses. The registry is on no hot path: it is asked to create an account, by the admin tool, and to forget a deleted one, and accounts never report to it. `stats` asks each account on demand.
- **The admin** is a secret `ADMIN_TOKEN`, compared in constant time, behind `/v1/admin/*`. It can see counts, sizes, times and ids, never content, and it can delete an account, not read one. Settings that must change without a deploy (`open_signup` and the caps) live in the registry and override the defaults in `wrangler.toml`.

**Quotas are enforced inside the account's own object**, so the registry is never on the request path: 50 MB stored, 2,000 log appends per UTC day, 6 devices, 1,000 log rows (which forces compaction), batches of at most 256 KB and snapshot parts of at most 1 MB, eight of them. Counters are held in memory and written every 20 appends, so an eviction can lose a few counts, which makes the cap slightly leaky and never unsafe. Over a cap the answer is `429 { code: "vault_quota", resetAt }`, and the app says when it resets and keeps everything pending. A relay-wide cap of 25 accounts is enforced at creation, and every cap can be changed by the admin without a redeploy.

### Free-tier facts

These are Cloudflare's Workers Free figures as read when this was designed; check the pricing page before relying on them. The relay needs only a free account and SQLite-backed Durable Objects (the only kind the free plan allows, hence `new_sqlite_classes`). The daily allowances are 100,000 requests, 100,000 rows written, 5 million rows read and 13,000 GB-s of Durable Object duration. When one is used up Cloudflare **fails the operation until 00:00 UTC and does not bill**; every device then shows the same paused state, retries with backoff up to half an hour, keeps everything pending, and local use is unaffected. That is told apart from a single account's quota because it is a server error, not a `vault_quota`. By the estimate in the design (assumptions, not measurements) a heavy user day is about 270 Durable Object requests, 600 rows written and, at worst, 350 GB-s, so the limits are two orders of magnitude above one person's use, and GB-s is the uncertain one. The honest figure is **25 to 50 regular users on the free plan**: measure GB-s from the dashboard first and raise the cap afterwards. The Durable Objects hibernate and run no timers or alarms (either would keep them awake); the client never polls on an error, backs off with jitter, and caps immediate retries, because a client bug that loops is the one thing that would defeat the arithmetic. Workers Paid ($5 a month) needs no code change and turns "the operation fails" into "you are billed", which is why the per-account and relay caps stay on in every mode.

Each origin is its own device (its own id, key copy and cursor): the GitHub Pages app, the desktop app on `127.0.0.1:47823`, and a desktop browser tab are three. `fetch` to a `workers.dev` address works from both with the CORS headers above, and the service worker of the web build never touches the relay: it skips anything with an `Authorization` header or going to a known relay host, and honours the relay's `cache-control: no-store` on the one call that has no header (`GET /v1/info`).

### What the relay can see, and not

It sees that an account exists and its id, creation and last-seen times, the number of devices, the size of each entry in padded buckets, how many entries a day, when a meter is running (presence is a message a minute), and the network address, which Cloudflare sees anyway. It does not see a record, a project or client name, an amount, a device name or a key. It can withhold, delay or reorder entries, serve an old snapshot, delete everything or refuse service; it cannot forge or alter a record. An account can be deleted by a device with a typed confirmation, which erases its storage and closes its sockets; other devices are told and offer to leave. A privacy notice, a named operator and an actual policy are different things, and only the first is in the app: before any public launch an operator owes users a policy, terms, a contact and a retention statement for Cloudflare's logs.

### Operating it

`npm run relay:deploy` is the whole first deploy in one command and safe to repeat: it makes the two secrets once into the git-ignored `relay/.admin.json` (never printed, and reused, because new ones would orphan every account), signs in to Cloudflare if needed, deploys with wrangler, hands both secrets to wrangler on standard input without a trailing newline, saves the address for the admin tool and checks that admin access works. `relay:init` makes the same secrets and prints the manual steps. `relay:admin` is a client of `/v1/admin`. `relay:local` runs the real Worker over database files on `127.0.0.1:8788` for development, refusing WebSockets with `426` so the app falls back to polling. See `relay/README.md`.

### How it is tested

No test touches a network, and the suite never uses a hand-written copy of the protocol where the real thing can run. The **vault and registry cores** run over `node:sqlite` in memory, which is why Node 24 is the toolchain. The **Worker and both Durable Object classes** run in Node against fake bindings (`tests/relayWorld.js`): `worker.js`, the cores and the SQL are real, and only the Durable Object runtime is a stand-in. The **client transport and engine** are driven against those real cores through a fetch-like shim, so if a shape in the core differed from what the client expects, a test fails; two or three simulated devices pair, sync, compact and fall far behind. The **built app in jsdom** talks to the same in-process Worker (`tests/app.integration.relay-helpers.js`), with the page's `fetch` throwing for any host that is not a relay. A fake relay (`syncFakeRelay.js`, `syncFakePairing.js`) remains for the engine and pairing tests that need a hostile or failing one, with hooks to rewrite what the relay hands each device. The **crypto** tests cover round trips, wrong AAD, epoch or part order, tampering, padding and wrapping. The **QR encoder** is checked without a decoder in the repository: the codewords are read back out of the matrix and must have zero Reed-Solomon syndromes in every block, the format and version fields must be valid and the fixed patterns in place; it was also decoded with two independent decoders. The **deploy and admin scripts** run against the real Worker with wrangler played by a fake.

What these cannot cover: the real Durable Object runtime (hibernation, billing, the real `wss://` upgrade), and a real Cloudflare account, CORS from the Pages origin and the installed phone app. Those are checked by hand against a deployed relay.

Cases worth knowing about:

- An 8-hour backgrounded tab still reports exactly 8 hours.
- A backwards clock jump clamps to zero rather than subtracting billable time.
- Starting a session closes any other open session on that project.
- A paused session stays the current session; a stopped one doesn't.
- Changing a project's rate from now on moves open tasks and leaves handed-in work alone; with the past included it moves the project, except a task with its own rate.
- Time over a task's limit pays its share, split inside the sitting that crossed it; a handed-in task keeps the limit it was handed in under.
- An overnight crash bills 2 hours to the last heartbeat, not the 11-hour gap.
- Startup reads storage exactly once, and rendering never reads or writes it.
- Two labels differing only by case or whitespace resolve to one task.
- A task's idle hours never land in its earned column.
- Re-filing a session moves its totals between tasks and leaves its hours and rate alone.
- A batch re-file skips deleted sessions.
- A task rate reprices finished sessions without touching their hours or their original snapshot.
- Clearing a task rate restores the recorded rate.
- Deleting a task keeps its hours and moves them to "No task".
- Correcting a session with a four-hour break bills 45m, not 5h45m.
- A second correction still preserves what the meter first recorded.
- A running session offers no edit link — stop it first.
- The desktop quit-guard treats a paused session as not running, and resolves any doubt as "safe to close".
- A long ledger starts collapsed, and its totals stay visible while collapsed.
- Weeks start Monday at local midnight, including across a DST shift — and including a week containing a day that has no local midnight at all.
- A session running 23:30 to 00:30 gives each day 30 minutes, and the week the full hour.
- Every day of a calendar year abuts the next exactly: no window overlaps its neighbour, and no bucket falls in a gap between them.
- A day that loses or gains an hour to DST is charted with 23 or 25 bars, and they still tile it exactly.
- The trend bars always sum to the headline figure for the period.
- Stepping a month back from the 31st lands on the 1st of the previous month, not in the one after it.
- A period with no predecessor reports no comparison rather than +0%.
- Off-clock hours never reach earnings, billed time, billable share or the breakdown — while the same data left on the clock inflates all four.
- A project with no `offClock` flag counts as work, so nothing recorded before the setting existed moves.
- A session whose project has been deleted counts as work, so reporting fails towards showing time you did record.
- Moving a project off the clock and back changes only how its hours are counted, never the hours.
- An off-clock project says activities, history and Start tracking; a work project still says tasks, ledger and Start the meter.
- Off the clock drops the idle split, the billable-hour rail and the money goal, and prints the elapsed figure once rather than twice.
- Work and Life are separate tabs; opening a project returns to the tab it belongs to.
- A life area is created with no rate at all, rather than a rate of zero to be explained away.
- An objective linked to a task reports hours spent against hours estimated; one with no link says so instead of implying zero.
- Deleting a task unfiles its objectives and keeps them.
- Today's focus is a calendar day, so it expires by itself and gathers work and life picks together.
- An objective can be linked to a task after it was written, and reports that task's hours the moment it is.
- A block entered by hand is marked as added, snapshots the current rate, and does not stop a meter that is running.
- Overlapping time is found across every project, ignores blocks that merely meet end to end, skips the gap inside a paused session, and needs explicit confirmation before it is recorded.
- Idle time never reaches an earnings total, a goal, or the cross-project headline.
- Starting idle stops the billed meter, so the same wall-clock hour is never counted twice.
- A session saved before idle tracking existed still counts as billed.
- Rejecting, reopening, handing in again and accepting pays a task's reward once, not twice.
- Handing a task in stops a meter still running on it before its hours are valued.
- A Kolkata or Auckland payday seen from Cairo or New York is the date the client's calendar says, not the day before.
- A cutoff at 02:00 on a Monday moves the forecast at 02:00, not at the next midnight.
- A reward shared across six tasks waits until the last of them gets there (accepted, or handed in where the project pays as worked), and then lands once.
- On a project paid as worked, handed-in work is dated from its hand-in, with nothing waiting; an answer after its week shut does not move it.
- A money goal counts money still waiting on an answer, and never rejected money.
- The desktop shell asks before closing on Settings nobody saved, and closes only when told to.
- A rate or price typed as "12,5" reads as 12.5; "-5", "abc" and "1,250" are refused and leave the task as it was.
- Editing one task and then another never carries the first one's values over.
- A sitting from 23:00 to 02:00 is listed under both days, and each day's rows add up to its heading.
- A week still going is compared with the week before up to the same weekday and time.
- Dollars and pounds in one period are never added together without a rate, nor divided by each other's hours.
- With live rates off, nothing is fetched on boot, on any tab, or from the ▾ menu; a converted figure is always marked `≈`; a currency with no rate falls back to each currency as earned, and a ranking never mixes converted and unconverted rows.
- Answering a payment while another currency is displayed stores the payment's own currency and cents.
- A ledger that cannot be parsed is copied aside before the first write, and never saved over.
- A relay test that passes against a hand-written fake and fails against the real core is a bug in the fake, which is why the client is driven against the real cores wherever it can be.
- Two copies of a record with the same stamp end identical on every device, whichever way they are merged.
- A list of records an older build has never heard of survives its sync and comes back unchanged.
- Nothing ephemeral (a heartbeat, presence) ever becomes pending, enters the log or is saved; losing the map of what was sent re-sends everything once and changes nothing.
- A join request from someone without the secret never reaches the owner's screen, and a wrapped key not proven to come from its holder is never opened.
- The vault key and device token are never in the JSON export; the deploy script prints neither of its secrets.
- Payments never add dollars to pounds; a payday has the same date in the history as it had in Upcoming; a paid line with no recorded day is dated by the payday rules and says so in the CSV.
- A CSV cell starting with `=`, `+`, `-` or `@` cannot run as a formula, and amounts stay numbers.
- Every test passes whatever the date it runs on: the suite has been run with the clock set to a Monday just after midnight, to the 1st of a month and to 1 January.
